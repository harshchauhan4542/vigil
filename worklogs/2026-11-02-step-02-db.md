# 2026-11-02 — Step 02: Database layer and audit log

**Session goal:** a typed database that works locally with no Docker, and the same code on Render.
**Result:** ✅ Done

## What was done

- `packages/db/src/schema.ts`: Drizzle schema for all plan tables (PayPal mirrors incl. `pp_orders`, `ledger_entries`, `exceptions`, `agent_runs`, `proposals`, `approvals`, `executions`, `idempotency_keys`, `webhook_events`, `audit_log`, `policies`, `recordings`).
- `client.ts`: driver switch. `postgres://` `DATABASE_URL` → `pg` Pool; otherwise PGlite (`.data/pglite` or `memory://`). `createTestDb()`, `queryRows()`.
- Migrations: `0000_init.sql` (drizzle-kit) + hand-written `0001_audit_log_append_only.sql` (trigger blocks UPDATE/DELETE/TRUNCATE).
- `audit.ts`: `appendAudit` (advisory lock, `hash = sha256(prev_hash + canonical_json(row))`) and `verifyChain`.
- `repositories.ts`: exceptions (upsert/re-open, transitions), proposals (DRAFT insert, one open per target, transitions), approvals (one per proposal, single-use token), executions, idempotency keys (reserve-before-call, reuse on retry, refuse a different body), webhook events (dedupe on `event_id`, transitions). Every status change uses the core state machine, checks the current state in the `UPDATE … WHERE`, and writes an audit row in the same transaction.
- `scripts/` workspace package: `pnpm db:migrate`, `pnpm audit:verify`.
- CI: new "DB migrations match the schema" step (fails if `schema.ts` changed without a migration).

## Decisions and deviations from the plan

- Money columns are `bigint` integer cents (`amount_cents`, …) instead of the plan's `numeric(12,2)`, per the hard rule.
- "One open proposal per target" is a partial unique index on `target_ref` alone (plan SQL had `(target_ref, action_type)`); this matches R6's wording "no other open proposal on the same target".
- `REVOKE UPDATE, DELETE` for the app role is deferred to Step 14 (Render): locally the app user owns the tables, so the trigger is the enforcement.
- Audit hash excludes `seq` (gaps after rollbacks are harmless); deletions are still caught via the `prev_hash` link.
