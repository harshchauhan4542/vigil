# 2026-11-02 — Step 05: Sandbox seeder

**Session goal:** realistic demo data in the sandbox, reproducible with one command.
**Result:** 🟡 Code done and tested against a fake PayPal; live run pending keys + sandbox accounts
**Branch / commit:** `step-05-seeder`

## What was done

- `packages/db`: tables `seed_objects` and `customer_notes` (migration `0002`), repositories in `src/seed.ts`.
- `scripts/src/seed/plan.ts`: stable seed keys for product, plan, 3 subscriptions, 4 AUTHORIZE orders (one above the $500 T2 cap), 4 CAPTURE orders (2 tracked, 2 untracked), optional dated cohort; `buildLedger()` with the three planted mismatches (missing fee on `cap:1`, wrong amount on `cap:2`, duplicate refund on `cap:3`); the prompt-injection note for `cap:4`.
- `scripts/src/seed/run.ts`: idempotent runner. Deterministic `PayPal-Request-Id` per seed key, so even a crash between PayPal's reply and the DB write re-uses the same order. Re-runs refresh status and finish orders the buyer has approved since.
- `scripts/src/seed/check.ts` + `pnpm seed:check`: re-reads every seeded object from the sandbox and prints the mix (kind × status, tracked, ledger rows, notes, pending approval links).
- `packages/paypal/src/sandbox-setup.ts`: `seedTracker` (so the seeder never imports `actions.ts`).
- Config: `SEED_CARD_NUMBER`, `SEED_CARD_EXPIRY` (defaults to a sandbox test Visa).
- 🧪 Spike S2 written up in `docs/spikes.md`.

## Decisions and deviations from the plan

- The duplicate refund is planted in the **books only** (two refund rows, no PayPal refund), because the seeder must not import the money-moving `actions.ts`. E4 should flag both rows as unmatched.
- The injection note is stored in `customer_notes` (support inbox, untrusted) linked to the `cap:4` order, and the order description says "see support note".
- Hold ages cannot be backdated in the sandbox; use `pnpm seed --cohort` daily (spike S2).
- Seed `ledger_entries` ids are UUIDv5 of the seed key, so re-runs insert nothing new.

## Problems and how they were solved

- `seed:check` first counted CREATED authorizations as "waiting for approval" → pending is now "subscription APPROVAL_PENDING, or an order with no authorization/capture yet" (caught by a test).
